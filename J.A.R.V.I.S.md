3. ЭТАП №2 — НОВЫЙ TTS ENGINE НА RUST

Создай новый проект:

"jarvis-tts-rs"

Используй:

- Rust stable.
- Tokio для асинхронной работы.
- Axum для HTTP API, если это оправдано.
- Serde для конфигурации и сериализации.
- Tracing для логирования.
- Подходящий нативный inference runtime.
- Структурированную обработку ошибок.

Сохрани модульную архитектуру.

Пример:

jarvis-tts-rs/
├── Cargo.toml
├── README.md
├── config/
│   └── default.toml
├── src/
│   ├── main.rs
│   ├── lib.rs
│   ├── config.rs
│   ├── api/
│   ├── engine/
│   ├── inference/
│   ├── audio/
│   ├── text/
│   ├── scheduler/
│   └── metrics/
├── tests/
└── benches/

Адаптируй структуру под реальную модель. Не создавай бессмысленных пустых модулей.

Главное требование

Новый TTS должен выполнять реальный синтез в Rust-процессе.

Запрещено использовать:
- Python-интерпретатор.
- PyO3 как способ запускать Python-инференс.
- Python subprocess.
- Вызовы старого Python TTS для генерации.
- Временный Python backend, выдаваемый за Rust.
- Фальшивые mock-ответы в финальном TTS.

Разрешены совместимые нативные runtime и библиотеки, вызываемые из Rust, включая FFI к нативным библиотекам, если они не требуют Python.

Например, ONNX Runtime, Candle или другой подходящий backend — только после проверки совместимости с фактической моделью.

Сохранение оригинальных весов и голосовых настроек имеет приоритет над выбором runtime.

Если существующая архитектура модели не поддерживается доступными Rust-совместимыми средствами, нужно честно показать причину, определить недостающие операции и предложить реальный способ их реализации.

Не подменять оригинальную модель другой без моего разрешения.

Новый Rust TTS должен максимально точно воспроизводить поведение старого движка.

Необходимо сохранить:

- Тембр.
- Голосовую идентичность.
- Произношение.
- Интонацию.
- Скорость речи.
- Паузы.
- Особенности оригинальной модели.

Не обучать новую голосовую модель без необходимости.

Если модель использует заранее подготовленные веса, speaker embeddings или reference audio, используй оригинальные данные согласно существующей реализации.

Создай сравнительные тесты.

Проверяй одинаковые тексты на старом и новом движках.

Не обещай идентичность побайтово, если генерация недетерминирована. Используй прослушивание и объективные измерения, где они применимы.

5. ПРОИЗВОДИТЕЛЬНОСТЬ И МНОГОПОТОЧНОСТЬ

Новый движок должен максимально эффективно использовать доступное серверное оборудование.

CPU

Исследуй:

- Rayon для CPU-bound задач, где он полезен.
- Выделенные рабочие потоки для инференса.
- Разделение асинхронного I/O и вычислительных операций.
- SIMD.
- NUMA.
- CPU affinity.
- Многопоточные tensor operations.
- Оптимизированные матричные операции.
- Переиспользование памяти.
- Минимизацию аллокаций.
- Работу без лишнего копирования аудиоданных.

Не запускай 40 параллельных потоков генерации только потому, что доступно 40 vCPU.

Найди оптимальное количество рабочих потоков экспериментально.

Особенно важно минимизировать задержку интерактивной речи, а не просто максимизировать общий throughput.

RAM

- Лимит: 20 GB.
- Модель должна загружаться один раз.
- Не загружай отдельную копию весов для каждого запроса.
- Реализуй управляемые очереди.
- Ограничь параллельные запросы.
- Не допускай неконтролируемого роста памяти.
- Предусмотри backpressure.

Storage

- Использовать не более 200 GB.
- Не хранить бесконечно промежуточные WAV-файлы.
- По возможности передавать аудио через память.
- Временные файлы своевременно очищать.
- Учитывать задержки HDD.

GPU

Предусмотреть возможность будущего перехода на GPU inference.

Однако текущая версия обязана работать без видеокарты.

6. ПОТОКОВАЯ ГЕНЕРАЦИЯ

Важнейшая задача — минимальная задержка до начала речи.

Не хочу ждать, пока модель сгенерирует длинный аудиофайл целиком.

Если архитектура модели позволяет, реализуй потоковую генерацию аудио по фрагментам.

Предусмотри:

- Streaming input.
- Incremental text processing.
- Audio chunk generation.
- Streaming output.
- Отмену запроса.
- Ограниченные буферы.
- Приоритет интерактивных запросов.
- Управление очередью синтеза.

Если сама модель не поддерживает внутренний потоковый инференс, реализуй синтез коротких законченных фраз с последовательной выдачей аудио.

Не называй это полноценным streaming inference, если движок фактически генерирует целые фразы.

7. HTTP API

Создай современный API для TTS-сервера.

Минимальные endpoints:

GET  /health
GET  /ready
POST /tts
POST /tts/stream
GET  /metrics

Streaming endpoint реализовать только с фактической поддержкой передачи аудио по частям. Можно выбрать WebSocket или подходящий HTTP streaming protocol.

Предусмотреть:
- Текст запроса.
- Настройки голоса.
- Формат аудио.
- Идентификатор запроса.
- Отмену синтеза.
- Ошибки с понятными кодами.
- Тайм-ауты.
- Контроль количества запросов.
- Аутентификацию.
- Настраиваемый адрес прослушивания.
- Защиту от несанкционированного доступа.

Не открывай TTS API во внешний интернет без защиты.

Для локального тестирования достаточно ограниченного доступа.

Performance benchmarks

Измерь:

1. Время загрузки модели.

Проведи серию воспроизводимых тестов.

Проверка сборки

Обязательно:

cargo fmt --check
cargo check --workspace
cargo clippy --workspace -- -D warnings
cargo test --workspace
cargo build --release

Исправь обнаруженные ошибки.

Запусти настоящий HTTP-сервер и проверь, что запрос на синтез возвращает корректное аудио.

Сохрани несколько тестовых аудиофайлов для прослушивания.

Проверь WAV-заголовки, частоту дискретизации, длительность и отсутствие повреждённых данных.
