# Система обновлений J.A.R.V.I.S. — план


## Context (зачем)
Сейчас Джарвис раздаётся вручную: собрал → ZIP → скинул в Telegram. Друг не узнает о новой версии, а каждая новая сборка весит ~300 МБ. Нужно: **выпустил релиз на GitHub → программа у всех сама увидела → скачала → обновилась**, без ручной пересылки, с понятными версиями и каналами (стабильная / бета / альфа).

Важно учесть:
- репозиторий `github.com/yuliitezarygml/jarvis` **публичный** → всё в Releases видит любой → **в релизах никогда не должно быть ключей и личных данных**;
- сейчас программа «портативная»: `config.json` и `data/` лежат рядом с exe (`src-tauri/src/config_store.rs` `resolve_config_path`). Обновление, которое заменяет файлы программы, не должно трогать настройки, память и ключи;
- тяжёлое (модель речи 215 МБ, база знаний 91 МБ) меняется редко — качать её при каждом обновлении нельзя.

## Как это будет выглядеть для пользователя
1. Джарвис при запуске и раз в 6 часов тихо проверяет GitHub.
2. Есть новая версия → в HUD плашка «Доступно обновление 0.3.0 — что нового: …» и голосом: «Вышло обновление. Поставить?» (фраза — по характеру).
3. «Обновить» (кнопка или голосом «да, обновляй») → скачивание с прогрессом → проверка подписи → Джарвис говорит «Перезапускаюсь» → установщик ставит новую версию поверх → Джарвис запускается сам. Настройки, память, ключи остаются.
4. Настройки → новая вкладка «Обновления»: текущая версия, канал (Стабильная / Бета / Альфа), «Проверять автоматически», «Ставить сразу, когда я не говорю» (вкл/выкл), кнопка «Проверить сейчас», список изменений.

## Версии: как называть
Стандарт **SemVer 2.0**: `МАЖОР.МИНОР.ПАТЧ[-метка.N]`, например `0.3.0`, `0.3.1`, `0.4.0-beta.2`.

| Часть | Когда растёт | Пример |
|---|---|---|
| МАЖОР | ломается совместимость (новый формат настроек/памяти без автопереноса). Пока проект молодой — `0.x` | `0.x` → `1.0.0` (первая «взрослая» версия) |
| МИНОР | новые возможности (характер, туннель голоса, обновления) | `0.2.0` → `0.3.0` |
| ПАТЧ | только исправления ошибок | `0.3.0` → `0.3.1` |

**Стадии (метки после дефиса)** — только 4 настоящие, остальное («дельта», «хуельта») в мире не используется и путает программы сравнения версий:

| Стадия | Пример | Кому | Что значит |
|---|---|---|---|
| **alpha** | `0.4.0-alpha.1` | только тебе | сырое, новые фичи, может падать |
| **beta** | `0.4.0-beta.3` | тебе и друзьям-тестерам | фичи готовы, ловим баги |
| **rc** (release candidate) | `0.4.0-rc.1` | бета-тестерам | «кандидат»: если за 2–3 дня багов нет — он и станет релизом |
| **стабильная** (без метки) | `0.4.0` | всем | проверено |
| (dev/nightly) | `0.4.0-dev.20261124` | только автосборка | необязательно, для ночных сборок |

Порядок сравнения (SemVer это гарантирует): `0.4.0-alpha.1 < 0.4.0-alpha.2 < 0.4.0-beta.1 < 0.4.0-rc.1 < 0.4.0 < 0.4.1`.

**Каналы** (выбор в настройках): «Стабильная» получает только `x.y.z`; «Бета» — `beta`, `rc` и стабильные; «Альфа» — всё. По умолчанию у друзей — «Бета», у тебя — «Альфа».

**Одна версия на весь проект**: `src-tauri/tauri.conf.json`, `src-tauri/Cargo.toml`, `package.json` (и `[workspace.package]` крейтов) — меняются одной командой (см. «Выпуск релиза»), тег git `v0.4.0-beta.2`.

## Архитектура
### 1. Что раздаём (ассеты релиза на GitHub)
| Файл | Что | Когда меняется |
|---|---|---|
| `JARVIS_0.4.0-beta.2_x64-setup.exe` | установщик NSIS (программа + DLL sherpa-onnx + словарь характера + CA сервера голоса), ~40–50 МБ | каждый релиз |
| `JARVIS_0.4.0-beta.2_x64-setup.exe.sig` | подпись обновления (ключ minisign, `tauri signer`) | каждый релиз |
| `content-stt-gigaam-v3-1.zip` | модель распознавания речи, 215 МБ | редко (своя версия) |
| `content-kb-2026.11.zip` | база знаний Windows, 91 МБ | редко (своя версия) |
| `SHA256SUMS.txt` | контрольные суммы всех файлов | каждый релиз |

**Манифесты каналов** — отдельный «служебный» релиз с тегом `updates` (его файлы перезаписываются при каждом выпуске): `stable.json`, `beta.json`, `alpha.json`. Адрес постоянный:
`https://github.com/yuliitezarygml/jarvis/releases/download/updates/beta.json`
(Почему не `releases/latest`: GitHub считает «latest» только стабильные, бет там не видно.)

Формат манифеста — стандартный для официального плагина Tauri (`version`, `notes`, `pub_date`, `platforms.windows-x86_64.{url, signature}`) + наше поле `content` (версии и адреса модели/базы знаний с sha256).

### 2. Как программа обновляется
- **Официальный плагин `tauri-plugin-updater`** (Tauri 2): проверяет манифест канала, сравнивает версии по SemVer, скачивает установщик, **проверяет подпись** публичным ключом, вшитым в программу (`tauri.conf.json` → `plugins.updater.pubkey`), запускает установку и перезапуск. Подделать обновление без закрытого ключа нельзя, даже если кто-то подменит файл.
- Закрытый ключ подписи — только у тебя (и в секретах GitHub Actions), **никогда не в репозитории**.
- Плюс `tauri-plugin-process` для перезапуска.
- Свой слой в Rust (`src-tauri/src/updates.rs`): выбор канала → адрес манифеста; расписание проверок; «не сейчас — напомнить завтра»; «ставить, когда не говорю» (ждать, пока нет задачи и речи — есть `busy`/`speaking` в `runtime`); события в HUD; голосовые фразы — через `Situation` из словаря характера (новые ситуации `UpdateAvailable`, `UpdateInstalling`).

### 3. Где живут настройки и данные (переезд из «портативного» режима)
- **Программа** (заменяется при обновлении): `C:\Users\<имя>\AppData\Local\Programs\JARVIS\` — установка «для текущего пользователя» (NSIS `currentUser`), чтобы обновление не требовало прав администратора на саму установку (сам Джарвис по-прежнему запускается от администратора).
- **Данные** (никогда не трогаются обновлением): `%APPDATA%\JARVIS\` → `config.json`, `data\memory.db`, `data\logs`, `data\voice-profile.json`, `persona\user.json` (словечки), а также скачанный контент `data\models`, `data\kb.sqlite`.
- Правка `resolve_config_path` (`src-tauri/src/config_store.rs:21`): порядок `JARVIS_HOME` → `config.json` рядом с exe (разработка и портативная сборка — как сейчас) → **`%APPDATA%\JARVIS\config.json`** (установленная версия). Проектная папка `d:\jarvis` продолжает работать как сейчас.
- Пути к ресурсам из установки (словарь характера `config/persona`, CA сервера голоса) — через `app.path().resource_dir()`, данные — от корня данных.
- **Миграции**: в `config.json` поле `config_version`; при запуске новой версии старые настройки переводятся автоматически (`jarvis-core`); у `memory.db` миграции уже есть (`PRAGMA user_version`). Перед обновлением — резервная копия `config.json` и `memory.db` в `%APPDATA%\JARVIS\backup\<версия>\` (последние 3).

### 4. Тяжёлый контент (модель речи, база знаний)
- В манифесте: `content.stt = { version, url, sha256, size }`, `content.kb = {…}`.
- При первом запуске или если версия контента в манифесте новее установленной → скачивание в фоне с прогрессом в HUD («Загружаю распознавание речи: 63 %»), проверка sha256, распаковка, переключение без перезапуска (STT/KB открываются заново).
- Пока модели нет — Джарвис работает через запасной путь (распознавание на сервере Xeon, если доступен) и говорит об этом.
- Обновление программы = ~45 МБ, контент качается только когда реально изменился.

### 5. Ключи и личные данные — никогда в релизе
- Установщик ставит **пустой** `config.json` (из `config.example.json`, голос — твой домен туннеля, характер — «Дворецкий» или по выбору).
- Ключи друг вводит сам в «Провайдеры», **или** ты передаёшь ему лично файл-приглашение `jarvis-invite.json` (только провайдеры и ключи) через Telegram → в Джарвисе «Настройки → Импорт» (или двойной клик по файлу). Так публичный GitHub никогда не видит ключей.
- Проверка перед выпуском (`tools/release`): в собранном установщике и ZIP нет строк, похожих на ключи (`gsk_`, `sk-or-`, `sk-`), и нет `memory.db`, `voice-profile.json`, `data/persona` (подколки ЖЖ без лицензии) — иначе выпуск останавливается.

### 6. Выпуск релиза (как ты будешь это делать)
Одна команда на твоём ПК — небольшая программа на Rust `tools/release` (без Python):
```
cargo run -p release -- 0.4.0-beta.2 --notes "Характер, туннель голоса, исправлено эхо"
```
Она: проверяет, что рабочее дерево чистое и тесты зелёные (`cargo test --workspace`, `npm test`) → ставит версию во все файлы → `CHANGELOG.md` (раздел версии) → коммит + тег `v0.4.0-beta.2` → `cargo tauri build` (NSIS, подпись обновления ключом из переменной окружения `TAURI_SIGNING_PRIVATE_KEY`) → проверка «нет ключей/личного» → `SHA256SUMS.txt` → загрузка ассетов в GitHub Release (через `gh`, нужен `gh auth login` один раз) → обновление манифестов в релизе `updates` по каналу (бета-версия попадает в `beta.json` и `alpha.json`, стабильная — во все три).

**Позже (необязательно):** то же самое в GitHub Actions на `windows-latest` по пушу тега — сборка в облаке, ключ подписи в секретах репозитория.

### 7. Откат и безопасность
- Подпись minisign на каждом обновлении (обязательна в плагине) + sha256 контента.
- Если новая версия не запустилась 2 раза подряд → при следующем запуске предложение «Вернуться на 0.3.1?» (ссылка на установщик прошлой версии из GitHub, он ставится поверх; данные целы благодаря резервной копии).
- Можно «заморозить» версию: Настройки → «Не обновлять до…».
- SmartScreen: без платной подписи кода Windows будет предупреждать при первой установке. Позже можно подключить Azure Trusted Signing (~10 $/мес) — предупреждение исчезнет. Обновления через плагин SmartScreen не трогает так сильно, как первую установку.

## Что меняется в коде (по этапам)
1. **Этап 1 — данные отдельно от программы**: `config_store.rs` (поиск `%APPDATA%\JARVIS`), ресурсы через `resource_dir`, первый запуск создаёт `config.json` из примера, импорт `jarvis-invite.json`, `config_version` + миграции, резервные копии. Тесты на порядок поиска и миграции.
2. **Этап 2 — установщик и подпись**: `tauri.conf.json` (NSIS `currentUser`, ресурсы, `plugins.updater` с pubkey и адресом манифеста `…/updates/{канал}.json`), `tauri signer generate` (ключ — вне репозитория, путь в инструкции), плагины `tauri-plugin-updater` + `tauri-plugin-process`, разрешения в `src-tauri/capabilities/default.json`.
3. **Этап 3 — проверка и установка в программе**: `src-tauri/src/updates.rs` (канал, расписание, «когда не говорю», события), вкладка «Обновления» в `src/components/settings/`, плашка в HUD, фразы в `config/persona/replies/*.json`.
4. **Этап 4 — контент отдельно**: загрузчик контента с sha256 и прогрессом, переоткрытие STT/KB без перезапуска.
5. **Этап 5 — `tools/release`**: версия везде, CHANGELOG, тег, сборка, проверка на ключи, SHA256SUMS, загрузка в GitHub, манифесты каналов.
6. **Этап 6 (позже)** — GitHub Actions и подпись кода.

## Проверка
- Тесты: сравнение версий и каналов (`0.4.0-beta.2` видна в «Бете», не видна в «Стабильной»), разбор манифеста, порядок поиска `config.json`, миграции, проверка «нет ключей в сборке», загрузчик контента (sha256 неверный → отказ).
- Живая проверка «обновление на себе»: собрать `0.3.0-beta.1`, установить → выпустить `0.3.0-beta.2` в канал → установленная программа сама находит, качает, ставит, перезапускается; настройки и память на месте; подменённый файл без подписи — отказ.
- Отдельный тестовый ПК/пользователь Windows (или друг) — чистая установка из релиза, ввод ключей через приглашение.

## Что нужно от тебя (один раз)
- `gh auth login` (вход GitHub CLI) — чтобы `tools/release` мог выкладывать релизы.
- Сохранить в надёжное место закрытый ключ подписи обновлений (потеряешь — старые установки не смогут обновиться, придётся переустанавливать вручную).
