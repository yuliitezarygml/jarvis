# Jarvis TTS · Rust

Самостоятельный сервер русской речи. Процесс Rust загружает исходные веса Shtorm-PocketTTS-RU fast, SentencePiece и голос Jarvis, подготавливает текст, получает акустические кадры и возвращает звук. Основное приложение Tauri получает звук по HTTPS.

## Запуск в этом проекте

Из каталога `jarvis-tts-rs` с Rust stable и локальными файлами `.assets/`:

```sh
cargo build --release --locked
(cd .assets && shasum -a 256 -c ../audit/model.sha256)
./target/release/jarvis-tts-rs
```

При первом запуске дождитесь записи `ready` в журнале. Для WAV и PCM с обычной скоростью достаточно Rust-бинарника и данных модели. Для MP3 или изменения скорости установите нативный FFmpeg с libmp3lame и atempo. Его путь задаётся через `JARVIS_FFMPEG`.

На чистом checkout скопируйте подготовленный комплект с сервера. Это самостоятельная копия операторских файлов, без виртуальных окружений. Она включает оригинальные параметры языковых моделей, словари и веса Silero, извлечённые из его архива, и оригинальную запись голоса. Файлы моделей исключены из Git.

```sh
mkdir -p .assets
ssh root@192.168.50.38 'tar -C /opt/jarvis-tts-rs/model -cf - .' | tar -C .assets -xf -
(cd .assets && shasum -a 256 -c ../audit/model.sha256)
```

## Рабочий экземпляр на Xeon

Служба `jarvis-tts-rs.service` запускает `/opt/jarvis-tts-rs/bin/jarvis-tts-rs` и слушает `https://192.168.50.38:8443`. Для сетевого интерфейса задайте `JARVIS_BIND`, `JARVIS_TLS_CERT`, `JARVIS_TLS_KEY` и `JARVIS_BEARER_TOKEN` в закрытом файле окружения службы. Сертификат частного центра для клиента находится в `src-tauri/config/xeon-tts-ca.pem`. Прежняя Python-служба и тестовый экземпляр Rust остановлены.

На настроенном Mac из корня проекта можно проверить готовность оригинального голоса. Команда читает токен из файла настроек и выводит HTTP-статус и результат проверки.

```sh
NODE_EXTRA_CA_CERTS=src-tauri/config/xeon-tts-ca.pem node \
  --env-file="$HOME/Library/Application Support/com.jarvis.desktop/backend.env" \
  -e 'fetch(process.env.JARVIS_TTS_URL+"/ready",{headers:{Authorization:"Bearer "+process.env.JARVIS_TTS_TOKEN}}).then(async r=>console.log(r.status,await r.text()))'
```

## API

| Запрос | Результат |
|---|---|
| `GET /health`, `GET /ready` | Живой HTTP-процесс и готовность загруженной модели. Сокет открывается после подготовки голоса. |
| `POST /tts` | JSON → WAV PCM16 mono 24 кГц или MP3. |
| `POST /tts/stream` | JSON → поток сырых сэмплов S16LE mono 24 кГц. Content-Type — application/octet-stream. |
| `POST /tts/stream` с `Content-Type: text/plain` | Поток UTF-8 → поток PCM. Перевод строки завершает фразу, EOF завершает последнюю. |
| `DELETE /tts/{id}` | Отмена ожидающей или активной генерации. 202 при принятии и 404 для неизвестного ID. |
| `GET /metrics` | Задания, суммарное ожидание очереди, число работ, завершившихся с ошибкой (включая прерванные), и время загрузки. |

Пример локального синтеза:

```sh
curl --fail --json '{"text":"Добрый вечер, сэр.","voice":"jarvis-ru","lang":"ru","format":"wav"}' \
  http://127.0.0.1:8181/tts -o jarvis.wav

curl --fail --no-buffer -H 'X-Request-Id: demo-1' \
  --json '{"text":"Проверка связи. Все системы работают."}' \
  http://127.0.0.1:8181/tts/stream | ffplay -nodisp -autoexit -f s16le -ar 24000 -ch_layout mono -i -
```

`speed` для готового файла — от 0,6 до 1,6. Потоковый режим использует обычную скорость. Поддерживаемый язык — русский. Английские слова и смешанный текст проходят через русский нормализатор. Клиент может заранее назначить `X-Request-Id` для отмены во время ожидания первого звука. Иначе сервер выдаёт UUID в ответе. Предел — 2000 символов и 90 секунд аудио. Ошибки до начала ответа возвращаются в JSON. После начала потока ошибка обрывает тело ответа, клиент должен отбросить его остаток.

## Устройство движка

- В `src/linguistics.rs`, `numeric.rs` и `stress.rs` выполняются нормализация и расстановка ударений. Candle исполняет исходные BERT/T5; словари, n-граммы и контекстный классификатор омографов используют извлечённые параметры Silero. Команда `prepare` читает строки stdin и выводит текст, подаваемый акустической модели.
- В `native/` выделен модельный адаптер из открытой **Rust**-реализации Kyutai, с указанием лицензии и ревизии в `native/NOTICE`. Он использует XN/xn-ptts, локальные файлы и SentencePiece. Новый сервер, очередь, языковой тракт, протокол и интеграция написаны отдельно. FlowLM и Mimi работают в одном процессе, веса и голос загружаются один раз. Между генератором латентов и декодером стоит ограниченный канал.
- Tokio/Axum обслуживают сеть, один выделенный рабочий поток обслуживает модель, декодер и общий Rayon-пул выполняют вычисления. В очереди одновременно допускаются до пяти заданий с учётом активного. Когда заняты все пять мест, новый запрос получает 429. Среди ожидающих первым выбирается запрос потока. Запущенный синтез прерывается отменой клиента. В очереди аудио четыре блока. Истечение 120 секунд или отключение клиента отменяет работу. Текст и звук обрабатываются в памяти.
- Граница будущего GPU-бэкенда — методы загрузки и покадрового синтеза в `src/engine.rs`. Текущий XN-адаптер типизирован для CPU. GPU потребует совместимого бэкенда и отдельного измерения точности/задержки.

## Эксплуатация и проверки

Для постоянной установки есть [systemd unit](deploy/jarvis-tts-rs.service). На целевой машине создайте системного пользователя `jarvis-rust-tts`, разместите исполняемые файлы в `/opt/jarvis-tts-rs/bin`, дайте группе сервиса доступ на чтение `model/`. В `/etc/jarvis-tts-rs.env` с правами 0600 задайте `JARVIS_BEARER_TOKEN`. На LAN укажите в настройках службы пути к сертификату и закрытому ключу TLS. Unit ограничивает память 6 GiB и вычисления десятью эквивалентами логического CPU. Число тензорных потоков по умолчанию — четыре. На Linux для сборки под этот Xeon использовалось `RUSTFLAGS="-C target-cpu=haswell"`. Отдельная проверочная установка заняла около 5,2 GiB вместе с компилятором и кэшем.

```sh
cargo fmt --check
cargo check --workspace
cargo clippy --workspace -- -D warnings
cargo test --workspace
cargo build --release --locked
node tools/check-text.mjs
```

При запущенном сервере `node tools/probe.mjs` проверяет синтез, валидацию, MP3, очередь, отмену и передачу звука до завершения загрузки текста. `node tools/queue-check.mjs` проверяет переполнение и восстановление. Исполняйте эти нагрузочные проверки на отдельном тестовом экземпляре. Node нужен только измерительному клиенту. Для сравнения Linux-потоков скрипт `tools/bench-linux.sh 1 2 4 6 8` запускает собственные временные units на порту 18182. Воспроизводимые примеры и ограничения приведены в [отчёте измерений](audit/results.md), исходная система описана в [аудите](audit/legacy.md).

### Постоянный экземпляр на Linux

На текущем сервере бинарник, FFmpeg, модель и сервисный пользователь уже подготовлены. Для отдельной установки с постоянным запуском подготовьте закрытый файл окружения, укажите свободный адрес (например, `JARVIS_BIND=127.0.0.1:8182`) и уникальный секрет `JARVIS_BEARER_TOKEN` длиной от 24 байт. Выполните команды из каталога проекта при вводе именно этого экземпляра в эксплуатацию:

```sh
sudo install -o root -g root -m 0644 deploy/jarvis-tts-rs.service /etc/systemd/system/jarvis-tts-rs.service
sudo chmod 0600 /etc/jarvis-tts-rs.env
sudo systemctl daemon-reload
sudo systemctl enable --now jarvis-tts-rs.service
sudo systemctl status jarvis-tts-rs.service
```

Проверьте `/ready` с учётными данными нового экземпляра и запрос WAV. Для диагностики используйте `journalctl -u jarvis-tts-rs.service`.

## Архив первоначального плана подключения

1. Согласовать голос на [парных аудиозаписях](examples/audio/). Затем в Rust Core определить интерфейсы для VAD/STT, потока текста LLM, клиента TTS и вывода PCM. Адрес TTS и выбор провайдера/модели читать из конфигурации, токены брать из защищённого хранилища на стороне Rust.
2. Проверить доступный идентификатор DeepSeek V4.1 Flash и поддержку потокового вывода в аккаунте OmniRouter. Первый адаптер возвращает текстовые фрагменты и поддерживает отмену. Тот же интерфейс позволяет выбрать другой доступный LLM. Разделитель завершённых фраз добавляет перевод строки и отправляет текст в один двунаправленный HTTP-запрос.
3. Для каждой реплики выделить идентификатор и ограниченную очередь PCM. Воспроизводить блоки по мере получения с ресемплингом под устройство. При обнаружении новой речи сразу остановить воспроизведение, очистить очередь, отменить запросы LLM и TTS и отбрасывать запоздавшие блоки по идентификатору.
4. Перед VAD/STT использовать акустическое эхоподавление с копией сигнала динамиков. Проверить на реальном микрофоне самораспознавание и прерывание пользователем во время речи. В Tauri передавать состояния прослушивания, ожидания и воспроизведения, а также уровень звука. Принятие этих тестов завершает этап подключения.
